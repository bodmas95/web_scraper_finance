## 1. Executive Summary

### Overview of the Project
The Financial Data Ingestion Pipeline is a comprehensive system designed to extract, process, and map financial data from annual reports and regulatory filings across three major regions: Americas (AMER), Asia-Pacific (APAC), and Europe, Middle East, and Africa (EMEA). The pipeline automates the extraction of financial statements and maps them to the standardized BREF (Banking Regulatory Reporting Framework) template format.

### Key Problem Statements and Results
- **Challenge**: Inconsistent data formats across different regions and regulatory frameworks
- **Solution**: Region-specific extraction pipelines with unified mapping methodology
- **Result**: Automated extraction and mapping of financial statements with 85%+ accuracy
- **Impact**: Reduced manual data entry time by 70% and improved data consistency

### Recommendations
1. Continuous enhancement of alias databases for improved field mapping accuracy
2. Implementation of automated quality checks for extracted data
3. Expansion of multilingual support for additional languages
4. Integration of machine learning models for pattern recognition in financial statements

## 2. Introduction

### Objectives and Problem Statement
The primary objective is to create a robust, scalable pipeline that can:
- Extract financial data from diverse sources (APIs, PDFs, XBRL files)
- Handle multiple regulatory frameworks (US GAAP, IFRS, local standards)
- Map extracted data to standardized BREF templates
- Support multilingual annual reports
- Provide user validation and correction capabilities

- **PDF Complexity**: Handling encoded PDFs, scanned documents, and various table formats
- **Data Structure Variability**: Different companies use varying formats for financial statements
- **OCR Accuracy**: Ensuring high accuracy for image-based PDFs
- **API Limitations**: Rate limits and data availability constraints

#### Regulatory Challenges
- **Framework Differences**: US GAAP vs IFRS vs local accounting standards
- **Reporting Variations**: Different terminology for similar financial concepts
- **Compliance Requirements**: Ensuring data extraction meets regulatory standards

#### Operational Challenges
- **Data Quality**: Handling missing, incomplete, or inconsistent data
- **Scalability**: Processing large volumes of reports efficiently
- **User Validation**: Balancing automation with manual review requirements

#### Privacy and Security
- **Data Protection**: Ensuring secure handling of financial information
- **Access Control**: Implementing proper authentication and authorization
- **Audit Trail**: Maintaining logs of all data modifications

### Scope of the Project
- **Geographic Coverage**: AMER, APAC, EMEA regions
- **Data Sources**: SEC EDGAR API, company websites, XBRL databases, manual uploads
- **Output Format**: BREF-aligned financial statements
- **Supported Statements**: Income Statement, Balance Sheet, Cash Flow Statement
- **Languages**: English, Chinese, and other major languages (with translation support)

## 3. Solution Overview

### Data Collection and Preparation

#### Region-Specific Extraction Methodologies

##### AMER (Americas) - SEC EDGAR API Integration
**Technology Stack**: SEC EDGAR API, Python requests library, JSON parsing

**Process Flow**:
1. **Company Identification**: Accept ticker symbol or CIK (Central Index Key) as input
2. **API Query**: Retrieve filing information from SEC EDGAR database
3. **Data Extraction**: 
   - Extract XBRL-tagged financial data
   - Parse standard concepts (us-gaap taxonomy)
   - Identify currency and reporting period
   - Extract all three financial statements (Income Statement, Balance Sheet, Cash Flow)
4. **Metadata Capture**: Store filing date, fiscal year, reporting currency, and accounting standards

**Technical Implementation**:
```python
# Example: Using SEC EDGAR API
- Endpoint: https://data.sec.gov/submissions/CIK{cik}.json
- Headers: User-Agent identification (required by SEC)
- Data Format: JSON with XBRL facts embedded
- Standard Concepts: us-gaap:Revenues, us-gaap:Assets, etc.
```

**Advantages**:
- Structured data with standardized taxonomy
- High accuracy due to regulatory requirements
- Automated currency and concept identification
- Historical data availability (10+ years)

**Challenges Addressed**:
- Handling multiple filing types (10-K, 10-Q, 8-K)
- Dealing with amended filings
- Managing rate limits (10 requests per second)

##### APAC (Asia-Pacific) - Web Crawling and PDF Extraction
**Technology Stack**: PDFPlumber, Selenium/BeautifulSoup, OpenAI Vision API, Tesseract OCR

**Process Flow**:
1. **Report Acquisition**:
   - **Automated Crawling**: Navigate company investor relations websites
   - **Manual Upload**: Support for direct PDF upload
   - **Historical Retrieval**: Fetch last 5 years of annual reports

2. **PDF Processing**:
   - **Format Detection**: Identify if PDF is text-based or image-based
   - **Text Extraction** (for text-based PDFs):
     ```python
     import pdfplumber
     with pdfplumber.open(pdf_path) as pdf:
         for page in pdf.pages:
             tables = page.extract_tables()
             text = page.extract_text()
     ```
   - **Table Extraction**: Use PDFPlumber's table detection algorithms
   - **Layout Analysis**: Identify financial statement sections

3. **Interactive Validation Interface**:
   - **Side-by-Side Display**: 
     - Left Panel: Extracted data in DataFrame format
     - Right Panel: Original PDF page image
   - **Real-time Editing**: Users can modify incorrect values before proceeding
   - **Visual Verification**: Highlight extracted regions on PDF image

4. **Encoded/Scanned PDF Handling**:
   - **Manual Page Selection**: User specifies page numbers for each statement
   - **LLM Vision Integration**:
     ```python
     # Using OpenAI Vision API
     - Search for keywords: "Income Statement", "Statement of Financial Position"
     - Identify table boundaries using visual recognition
     - Extract table structure and values
     - Apply OCR for text recognition
     ```
   - **Table Reconstruction**: Convert visual table to structured data

**Technical Deep Dive - PDFPlumber**:
- **Table Detection Algorithm**: Uses vertical/horizontal line detection and text clustering
- **Cell Extraction**: Identifies cell boundaries based on whitespace and separators
- **Text Alignment**: Preserves column alignment for accurate data extraction
- **Custom Settings**: Adjustable parameters for table detection sensitivity

**Advantages**:
- Handles diverse PDF formats
- User validation ensures accuracy
- Supports both automated and manual workflows
- Visual feedback improves user confidence

**Challenges Addressed**:
- Complex table layouts (merged cells, nested tables)
- Multi-page financial statements
- Inconsistent formatting across companies
- Language barriers (Chinese, Japanese, Korean)

##### EMEA (Europe, Middle East, Africa) - XBRL API Integration
**Technology Stack**: XBRL API, LEI (Legal Entity Identifier) lookup, IFRS taxonomy parser

**Process Flow**:
1. **Entity Identification**: Use LEI as primary identifier
2. **XBRL Retrieval**: Query XBRL databases (e.g., ESEF, national repositories)
3. **Concept Mapping**: Extract data using IFRS taxonomy concepts
4. **Data Structuring**: Convert XBRL facts to tabular format
5. **Currency Normalization**: Handle multiple currencies (EUR, GBP, etc.)

**Technical Implementation**:
```python
# IFRS Concept Examples
- ifrs-full:Revenue
- ifrs-full:Assets
- ifrs-full:ProfitLoss
- Context handling: Period, entity, dimensions
```

**Advantages**:
- Standardized IFRS taxonomy
- Structured data with semantic meaning
- Regulatory compliance built-in
- Multi-currency support

**Challenges Addressed**:
- Different XBRL implementations across countries
- Extension taxonomies (company-specific concepts)
- Dimensional data (segments, geographical areas)

### Fine-Tuning Process

#### Alias-Based Matching Methodology

**Evolution of Mapping Approach**:

**Phase 1 - Value Matching (Initial Approach - Deprecated)**:
- **Method**: Match fields based on numerical values and year-over-year comparisons
- **Problems Encountered**:
  - Low accuracy due to similar values across different line items
  - Failed to capture semantic meaning of field labels
  - Could not handle new or unique line items
  - Limited reference fields caused incomplete mappings

**Phase 2 - Alias-Based Matching (Current Approach)**:
- **Method**: Maintain comprehensive alias databases for each BREF field
- **Process**:
  1. **Alias Database Creation**:
     ```python
     FIELD_MAPPINGS = {
         "Q1 | Sales (Revenue)": {
             "aliases": [
                 "Revenue", "Sales", "Turnover", "Operating Revenue",
                 "Total Revenue", "Net Sales", "Gross Sales"
             ]
         },
         "Q28 | Interest costs (gross)": {
             "aliases": [
                 "Finance Costs", "Interest Expense", "Borrowing Costs",
                 "Cost of Borrowing", "Finance Charges"
             ]
         }
     }
     ```
  
  2. **Normalization Process**:
     ```python
     def normalize_label(label):
         # Convert to lowercase
         normalized = label.lower().strip()
         
         # Remove non-ASCII characters (Chinese, special chars)
         normalized = re.sub(r'[^a-z0-9\s\-&/(),.]', '', normalized)
         
         # Handle singular/plural variations
         # "Accounts Payables" -> "account payable"
         
         # Remove punctuation
         # "Finance costs (gross)" -> "finance costs gross"
         
         return normalized
     ```
  
  3. **Matching Algorithm**:
     - **Exact Match**: Normalized label matches normalized alias
     - **Fuzzy Match**: Token-based similarity (threshold: 75%)
     - **LLM Fallback**: Use GPT-4 for complex cases

**Phase 3 - Multilingual Support**:
- **Challenge**: Reports in Chinese, Japanese, Korean, etc.
- **Solution**:
  1. **Language Detection**: Identify report language
  2. **Translation**: Use LLM to translate to English
     ```python
     # Example: "融资成本" (Chinese) -> "Finance costs"
     # After normalization: "finance costs" -> matches alias
     ```
  3. **Dual-Language Handling**: Process labels like "Finance costs 融资成本"
     - Remove Chinese characters: "Finance costs"
     - Match against English aliases

**Phase 4 - Format Standardization**:
- **Challenge**: Different data formats from XBRL (AMER/EMEA) vs PDF (APAC)
- **Solution**: Unified data transformation pipeline
  ```python
  # XBRL Format (AMER/EMEA)
  {
      "concept": "us-gaap:Revenues",
      "value": 1000000,
      "period": "2024-12-31",
      "currency": "USD"
  }
  
  # PDF Extraction Format (APAC)
  {
      "label": "Revenue 营业额",
      "2024": 1000000,
      "2023": 950000,
      "currency": "HKD"
  }
  
  # Unified Output Format (BREF-aligned)
  {
      "bref_code": "Q1",
      "label": "Sales (Revenue)",
      "value_2024": 1000000,
      "value_2023": 950000,
      "currency": "USD",
      "mapping_confidence": "high",
      "mapping_method": "alias_match"
  }
  ```

## 4. Experiments and Results

### Description of Experiments

#### Experiment 1: Alias Database Effectiveness
- **Objective**: Measure improvement in mapping accuracy with alias-based approach
- **Method**: Compare value-matching vs alias-matching on 100 sample reports
- **Results**: 
  - Value-matching: 45% accuracy
  - Alias-matching: 87% accuracy
  - Improvement: +42 percentage points

#### Experiment 2: Multilingual Translation Impact
- **Objective**: Assess translation quality and mapping accuracy for non-English reports
- **Method**: Process 50 Chinese annual reports with and without translation
- **Results**:
  - Without translation: 12% mapping success
  - With translation: 82% mapping success
  - Translation accuracy: 95% (manual validation)

#### Experiment 3: PDFPlumber vs OCR Performance
- **Objective**: Compare extraction accuracy for different PDF types
- **Method**: Test 200 PDFs (100 text-based, 100 image-based)
- **Results**:
  - Text-based PDFs (PDFPlumber): 94% accuracy
  - Image-based PDFs (OCR): 78% accuracy
  - Hybrid approach: 89% overall accuracy

### Error Analysis

#### Common Extraction Errors
1. **Merged Cells**: PDFPlumber struggles with complex table layouts
2. **Multi-line Headers**: Difficulty identifying correct column headers
3. **Footnotes**: Incorrectly included in table data
4. **Currency Symbols**: Misinterpreted or missing

#### Common Mapping Errors
1. **Synonym Variations**: "P&L" vs "Income Statement" vs "Statement of Operations"
2. **Hierarchical Mismatches**: Parent vs child line items
3. **Regional Terminology**: US GAAP vs IFRS naming differences
4. **Company-Specific Terms**: Unique labels not in alias database
